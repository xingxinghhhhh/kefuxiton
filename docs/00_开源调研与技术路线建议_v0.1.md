# AI 智能客服 Agent：开源调研与技术路线建议

文档状态：评审草案（Draft）  
版本：v0.1  
调研日期：2026-08-07  
用途：立项前技术与产品共识，不作为最终采购、法务或架构批准

## 1. 结论

AI 客服 Agent 不是“接入一个大模型的聊天窗口”。工作产品至少要处理会话与渠道、企业知识检索、引用与不确定性、转人工、业务工具权限与审计，以及知识和回答质量的持续运营。

开源能力分层：

| 能力层 | 代表项目 | 适合作用 |
|---|---|---|
| 客服工作台/多渠道 | Chatwoot | 收件箱、客服协作、标签、分配、人工接管 |
| AI 应用与 RAG | Dify、FastGPT、MaxKB | 知识库、工作流、Agent、模型接入、应用日志 |
| 可控对话流程 | Rasa | 强约束流程；当前仓库处于 Maintenance Mode，不建议作为默认底座 |
| Agent 流程开发 | Langflow | 原型、流程实验、API/MCP 暴露 |
| 通用业务自动化 | n8n | 外部连接和自动化验证；商业使用必须单独审查许可证 |

## 2. 推荐路线

采用“薄定制层 + 可替换 AI 能力”：首个运行版本只做 Web Chat、一个业务领域、一个知识库和一套人工接管闭环；用 Dify/FastGPT/MaxKB 任选其一做技术验证，不先深度 Fork；客服收件箱可评估 Chatwoot，但会话网关、权限、业务工具适配、审计、质量评测和数据归属由项目掌握。

许可证不能仅凭项目名称判断。Dify、FastGPT、MaxKB、Chatwoot、Rasa、Langflow、n8n 均需按实际版本、目录和商业模式逐项审查。

## 3. 推荐架构分层

```text
客户渠道 -> 会话网关 -> Agent 编排层 -> 知识库检索
                                  -> 业务工具适配层
                                  -> 安全与策略层
                                  -> 人工接管工作台
                                  -> 日志、评测与运营
```

- 会话网关负责鉴权、消息标准化、会话 ID、幂等、限流和渠道回调。
- Agent 编排层负责判断问题类型、选择检索/工具、生成回答、重试和转人工，不拥有超出业务需要的写权限。
- 知识库负责版本、解析、切片、检索、重排、引用、失效和回滚；上传文件不等于知识可信。
- 业务工具通过显式契约接入，MVP 只做只读查询。
- 客服必须看到原始问题、AI 回答、引用、工具调用、失败原因和建议动作。

## 4. 选型门槛

在最终锁定技术栈前，必须确认：商业模式、数据是否允许发送第三方模型、首个业务领域、首期渠道、人工流程、合规范围和交付目标（Demo/试点/生产）。

## 5. 研发顺序

1. 需求与证据确认：业务访谈、脱敏样本、领域/渠道确认、许可证和数据边界审查。
2. 单领域 Web Chat MVP：知识导入/审核/发布/回滚、引用、拒答、转人工、反馈、评测。
3. 客服工作台与只读业务工具：队列、分配、标签、备注、可追踪工具调用。
4. 多渠道和受控写操作：每个写操作先人工审批或用户二次确认，建立回归和红队门禁。

## 6. 明确不做

不以拟人化作为上线标准；不把向量命中当作事实正确；不允许默认退款、删除、改账、改址；不在没有真实数据和业务确认时承诺准确率、ROI 或节省人数；不把许可证理解为法律意见。

## 7. 评审结论

建议先批准“单领域、单渠道、可人工接管、只读知识问答”的 MVP。第一个成功标准是：在真实工作流中稳定回答明确问题，不能回答时可靠转人工，并且每个回答可解释、可追溯、可评测。
