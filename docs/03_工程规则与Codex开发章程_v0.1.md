# AI 智能客服 Agent 工程规则与 Codex 开发章程

版本：v0.1  
日期：2026-08-09  
状态：代码开发前规则草案  
目的：作为公司内部评审材料，以及仓库 `AGENTS.md` 的人类可读说明。

## 1. 规则如何生效

可执行规则写入仓库根目录 `AGENTS.md`，后端、前端、接口契约和测试规则写入对应目录的 `AGENTS.md`。Codex 开始工作前读取这些文件；越靠近当前工作目录的规则覆盖上层同名指导。根规则保持稳定，模块规则只写本模块特有约束。

本文件用于人类评审，不替代实际的 `AGENTS.md`。规则最终必须由 lint、类型检查、测试、评测和 CI 共同执行，不能只依赖模型记忆。

## 2. 已冻结的前提

- 首期是单 Web Chat、单业务领域、单知识库。
- 首期核心闭环是知识问答、来源引用、保守拒答和人工接管。
- 首期工具只读，不做退款、改账、改地址、删除和支付操作。
- 不把 Dify、FastGPT、MaxKB 或 Chatwoot 深度 Fork 成项目核心。
- AI、检索、向量库、客服工作台和业务系统都必须可替换。
- 不使用生产客户数据做普通开发和测试。
- 不在需求、权限、数据和许可证未确认前扩展功能。

## 3. 工程技术基线

| 层 | 基线 | 约束 |
|---|---|---|
| 工作区 | pnpm workspace | 依赖集中管理，锁文件必须提交 |
| 后端 | NestJS + TypeScript strict | REST/OpenAPI，Controller 薄，按领域模块拆分 |
| 数据 | PostgreSQL + Prisma | ORM 只在基础设施层，迁移可审查、可回滚 |
| 前端 | Next.js App Router + React + TypeScript | Server Component 默认，Client Component 最小化 |
| UI | Tailwind CSS + 可访问组件层 | 不牺牲语义、键盘操作和移动端体验 |
| 测试 | Jest/Vitest + Testing Library + Playwright | 统一脚本入口，禁止依赖真实生产服务 |
| AI | Provider/Adapter 抽象 | 领域层不依赖具体模型或开源平台 SDK |
| 质量 | ESLint、Prettier、TypeScript、覆盖率、离线评测 | 规则必须可自动验证 |

版本号在项目 bootstrap 时通过官方文档和公司运行环境确认并锁定，Codex 不得自行升级框架或替换 ORM。

## 4. 模块开发顺序

基础工程 -> 身份与权限 -> 会话与消息 -> 知识库 -> 检索与 Agent -> 人工接管 -> Web Chat -> 客服工作台 -> 离线评测与运营 -> 只读业务工具。

不要先开发多渠道、复杂 UI、自动化写操作或“通用 Agent”，再回头补基础治理。

## 5. 单节点开发节奏

```text
确认需求 -> 写验收标准 -> 设计接口和数据 -> 实现最小后端 ->
实现最小前端 -> 补齐单元/集成/E2E/评测 -> 运行门禁 -> 记录结果和风险
```

节点大小以“一个人可以审查、测试和回滚”为准，不得同时修改不相关的领域、框架、部署方式和数据模型。

## 6. 交付与审查

每次交付必须报告节点目标、变更文件、API/数据库/权限/用户行为变化、验证命令及结果、未验证问题和唯一下一节点。

需要单独评审的变更包括：更换框架、引入新生产依赖、接入新模型、扩大数据权限、增加写工具、改变会话/知识数据结构、引入多租户、接入新渠道、深度修改开源项目、改变许可证或生产部署方式。

人工审查必须确认：需求无越界、保留人工接管、回答有知识或工具依据、无跨用户或敏感信息泄露、无模型自主写操作、失败可解释/可重试/可转人工、迁移和配置可回滚、测试覆盖异常和安全边界、接口/运行手册/评测数据已更新。
